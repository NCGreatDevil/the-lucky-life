# 随机事件功能说明书

---

## 1. 概述

本文档定义一套完整的随机事件系统，涵盖事件触发、属性增减、人物偶遇（NPC与真人）及好感度培养等模块。运气属性贯穿始终，影响事件走向与结果，同时保持"有得有失"的平衡体验。

### 核心设计理念

- 运气影响无处不在，但永不绝对（好运可能遇挫，厄运亦存转机）。
- 事件提供多选项，每个选项均为得失权衡，鼓励策略选择。
- 人物偶遇结合随机性与匹配算法，营造真实社交感。
- 全配置化后台，便于策划动态调整内容与数值。

## 3. 事件基础设定

### 3.1 事件分类

事件有两个维度：

**维度一：触发方式（trigger_type）**

| 触发方式 | 说明 | 消耗 |
|----------|------|------|
| active（主动） | 玩家在事件页面主动点击按钮触发 | 能量 -10 |
| passive（被动） | 系统自动生成，推送给玩家 | 能量 -5 |

**维度二：内容分类（category）**

| 分类 | 说明 |
|------|------|
| normal（普通） | 不关联人物，纯情景事件 |
| npc（NPC） | 关联特定NPC，触发人物偶遇 |
| friend（好友） | 关联真人用户，触发真人偶遇 |

两个维度组合，共 3×2=6 种事件类型，存储在同一张事件表中。

### 3.2 事件配置结构

| 字段 | 类型 | 说明 |
|------|------|------|
| id | TEXT | 唯一标识 |
| name | TEXT | 前端显示标题 |
| description | TEXT | 情景文本（可富文本） |
| image_url | TEXT | 配图资源路径 |
| category | TEXT | normal / npc / friend |
| trigger_type | TEXT | active / passive |
| npc_id | TEXT | NPC类事件关联具体NPC；friend类可为具体用户ID或 'all'（随机）；normal类为 NULL |
| luck_tier | INTEGER | 事件归属的运气档位(1-6)，影响抽取概率 |
| enabled | INTEGER | 启用状态（0/1） |
| created_at | TEXT | 创建时间 |

### 3.3 选项配置结构

每个事件包含2-4个选项，每个选项定义独立效果：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | TEXT | 唯一标识 |
| event_id | TEXT | 关联事件ID |
| option_order | INTEGER | 选项序号 1/2/3/4 |
| option_text | TEXT | 按钮显示文案 |
| effects | TEXT | JSON数组，定义影响的属性及基础范围 |

**effects JSON 结构示例：**

```json
[
  {"attr": "energy", "range": [-10, -5]},
  {"attr": "popularity", "range": [1, 5]},
  {"attr": "luck", "range": [1, 3]}
]
```

- `attr`：属性名（对应数据库字段名）
- `range`：`[min, max]`，策划配置的基础范围，不要求对称，不要求一定有正有负

## 4. 事件触发机制

### 4.1 主动事件触发

- **触发方式**：玩家在事件页面点击按钮
- **消耗**：能量 -10（能量不足时无法触发）
- **次数限制**：无限制，只要能量足够即可反复触发
- **触发流程**：走完整抽取流程（见第5节）
- **属性联动**：每次触发后立即更新属性（运气可能因事件改变），下次触发以最新属性为准

### 4.2 被动事件触发

被动事件由系统自动生成，用户无需主动操作。分为两类来源，**共同计入当日被动事件数**。

#### 4.2.1 第一类：定时生成

- 每日固定生成 **3个** 被动事件
- 生成时间点：**0:00、8:00、16:00**
- 每个事件自生成时刻起保留 **16小时**，过期自动清除
- 对所有用户生效（无论在线与否）

#### 4.2.2 第二类：登录触发

- 基于用户当日**登录次数**（产生登录日志的次数）递减概率触发
- 概率公式：`P = 1 / 2^(n-1)`，其中 n 为当日第几次登录尝试

| 登录次数 n | 触发概率 |
|-----------|---------|
| 1（当日首次） | 100% |
| 2 | 50% |
| 3 | 25% |
| 4 | 12.5% |
| 5 | 6.25% |
| ... | ... |

- **登录次数计数规则**：每次产生登录日志（login_logs）即计数+1，无论是否成功触发事件
- **定时器代执行**：若用户在定时器触发时处于在线状态，定时器代为执行一次登录触发逻辑（消耗一次登录尝试次数）


#### 4.2.3 两类协同示例

假设某用户一天的行为：

| 时间 | 事件 | 说明 |
|------|------|------|
| 00:00 | — | 定时器重置当日状态 |
| 02:00 | 定时器触发 | 生成第1个定时事件；用户在线，代为执行登录触发（n=1，100%）→ 再生成1个事件。**此时共2个被动事件** |
| 02:10 | 用户退出 | — |
| 02:30 | 用户登录 | 产生登录日志，n=2，50%概率触发 |
| 08:00 | 定时器触发 | 生成第2个定时事件；用户若在线，代为执行登录触发（n=3，25%） |
| 16:00 | 定时器触发 | 生成第3个定时事件；用户若在线，代为执行登录触发（n随实际登录次数递增） |

#### 4.2.4 被动事件展示

- 被动事件生成后，出现在**专门的事件记录页面**
- 右上角**铃铛图标**显示当前未处理事件数
- 用户点击进入后，可查看/响应事件

#### 4.2.5 补充说明

- 由于被动事件的触发需要消耗5点能量，但是如果能量不足时，将跳过该次触发。无论是第一类和第二类都是一样。

### 4.3 主动/被动事件的共同点

- 均走相同的**事件抽取流程**（见第5节）
- 均可能触发**人物偶遇**（NPC或真人）
- 均会**更新用户属性**（运气可能变化，影响后续事件）
- 均记录到**事件历史**

## 5. 事件抽取流程

无论是主动还是被动触发，均执行以下流程：

### 5.1 整体步骤

```
步骤1：确定当前运气
  → 获取玩家今日运气值 → 映射为运气等级 L（1~6）

步骤2：抽取档位
  → 50% 概率使用当前档位 L
  → 20% 概率使用低一级档位（最低1）
  → 30% 概率使用高一级档位（最高6）
  → 得到目标档位 T

步骤3：人物偶遇判定
  → 基础概率 = 15% + 当前运气等级 L（%）
  → 掷骰决定是否遇人
  → 若遇人：50%为NPC，50%为真人

步骤4：事件池过滤
  → 根据目标档位 T、事件分类（normal/npc/friend）、启用状态筛选候选事件
  → 优先选择玩家未曾触发过的事件（去重）
  → 若所有事件均已触发过，则随机抽取（记录重复触发次数）

步骤5：随机抽取
  → 从符合条件的候选事件中等概率选取一个

步骤6：事件展示
  → 前端呈现事件描述、图片、选项按钮

步骤7：结果结算
  → 玩家选择选项后，后端计算属性变化、好感度变化、人物关系等
  → 返回结果给前端展示
```

### 5.2 事件去重与重复触发

- 每个事件记录玩家触发次数（默认0表示未触发）
- 抽取时优先选择触发次数为0的事件
- 当所有候选事件触发次数均≥1时，随机选取一个，触发次数+1
- 以此实现"优先不重复，全触发过后循环"

### 5.3 事件池数量配比建议

| 运气档位 | 占比建议 |
|----------|----------|
| 1（倒霉） | 10% |
| 2（不顺） | 20% |
| 3（平常） | 40% |
| 4（顺遂） | 15% |
| 5（好运） | 10% |
| 6（爆棚） | 5% |

## 6. 属性增减计算规则

### 6.1 运气修正公式

对于任意基础范围 `[min, max]`，给定运气等级 L（1~6），计算实际生效区间：

**定义：**
- `span = max - min`（区间跨度）
- `p = (L - 1) / 5`（倾向度，L=1时p=0，L=6时p=1）

**公式：**
```
actual_min = round(min + p × (span - 1))
actual_max = round(max - (1 - p) × (span - 1))
```

**特性：**
- 运气越好（p越大），区间整体向 max 偏移
- 运气越差（p越小），区间整体向 min 偏移
- 区间宽度至少为1（不会坍缩为单点）
- 若 span ≤ 1，区间保持不变
- actual_min 始终 ≥ min，actual_max 始终 ≤ max（不突破原始边界）

**示例1：`[-2, 4]`（span=6）**

| L | p | actual_min | actual_max | 实际区间 |
|---|----|-----------|------------|---------|
| 1 | 0.0 | -2 | -1 | [-2, -1] |
| 2 | 0.2 | -1 | 0 | [-1, 0] |
| 3 | 0.4 | 0 | 1 | [0, 1] |
| 4 | 0.6 | 1 | 2 | [1, 2] |
| 5 | 0.8 | 2 | 3 | [2, 3] |
| 6 | 1.0 | 3 | 4 | [3, 4] |

**示例2：`[0, 4]`（span=4，纯正向）**

| L | p | actual_min | actual_max | 实际区间 |
|---|----|-----------|------------|---------|
| 1 | 0.0 | 0 | 1 | [0, 1] |
| 2 | 0.2 | 0 | 2 | [0, 2] |
| 3 | 0.4 | 1 | 2 | [1, 2] |
| 4 | 0.6 | 1 | 3 | [1, 3] |
| 5 | 0.8 | 2 | 3 | [2, 3] |
| 6 | 1.0 | 3 | 4 | [3, 4] |

运气最差时 min 仍为0，不会变成负数。

**示例3：`[1, 3]`（span=2，纯正向窄区间）**

| L | p | actual_min | actual_max | 实际区间 |
|---|----|-----------|------------|---------|
| 1 | 0.0 | 1 | 2 | [1, 2] |
| 2 | 0.2 | 1 | 2 | [1, 2] |
| 3 | 0.4 | 1 | 2 | [1, 2] |
| 4 | 0.6 | 2 | 3 | [2, 3] |
| 5 | 0.8 | 2 | 3 | [2, 3] |
| 6 | 1.0 | 2 | 3 | [2, 3] |

> 窄区间（span=2）时，运气影响较小：L1~L3 均为 `[1,2]`，L4~L6 均为 `[2,3]`。区间跨度越大，运气修正效果越明显。

### 6.2 不受运气修正的属性

以下属性**不经过运气修正**，直接在策划配置的 `[min, max]` 范围内随机取整：

| 属性 | 原因 |
|------|------|
| money（金钱） | 消耗型属性，与运气无关 |
| energy（能量） | 日常属性，仅作为事件消耗 |
| vitality（活力） | 日常属性，仅作为事件消耗 |

### 6.3 最终数值生成流程

1. 玩家触发事件后选择某选项
2. 遍历该选项的 effects 列表：
   - 若 attr 为 money / energy / vitality：在 `range` 内直接随机取整
   - 若 attr 为其他属性：取 `range` 的 min/max，按运气修正公式计算实际区间 `[actual_min, actual_max]`，从中随机取整
3. 将得到的值叠加到对应属性上
4. 能量上限为100，超出部分截断

## 7. 人物偶遇系统

### 7.1 NPC偶遇

#### 7.1.1 NPC数据管理

**数据库存储（共性信息）：**

| 字段 | 说明 |
|------|------|
| id | NPC唯一标识（如 'taizai_npc'） |
| name | 名称 |
| avatar | 头像/emoji |
| title | 称号 |
| description | 描述 |
| personality_prompt | 性格Prompt文本 |
| rules_json | 对话规则JSON数组 |
| greeting_hours_json | 分时问候语JSON |

| conversation_rounds_max | 最大对话轮数 |

**代码类保留（个性行为）：**
- `getSystemPrompt()` — 组装完整prompt
- `getDynamicContext()` — 动态上下文
- `processUserInput()` — 处理用户输入状态
- `shouldRefuseReply()` — 判断是否中断对话
- `getRefusalReason()` — 获取中断理由

#### 7.1.2 好感度系统

**获取方式：**
- 每次通过事件遇到NPC时，随机增加 **1~50** 点好感度
- 首次遇到该NPC时，好感度**翻倍**（2~100点）
- 好感度不受运气修正影响

**等级经验规则：**

| 等级 | 所需累计经验 | 公式 |
|------|-------------|------|
| LV0 | 0 | — |
| LV1 | 100 | 100 × 1 |
| LV2 | 300 | 100 × (1+2) |
| LV3 | 600 | 100 × (1+2+3) |
| LV4 | 1000 | 100 × (1+2+3+4) |
| LVn | 100 × n(n+1)/2 | — |

### 7.2 真人偶遇

#### 7.2.1 匹配算法

**目标**：找到"性格方向相近 + 数值水平接近"的真人玩家。

**参与匹配的属性（7项）：**
morality（道德）、intelligence（智力）、constitution（体质）、charm（魅力）、willpower（意志）、emotion（情绪）、popularity（人缘）

**匹配流程：**

1. 获取当前玩家的前三高属性名及数值（降序排列），记为 `[A1, A2, A3]`，对应值 `[V1, V2, V3]`
2. 若所有7项属性均为0（极端情况），**跳过真人匹配，改为遇到NPC**
3. 候选池：所有未被当前玩家添加为好友的真实玩家

---

**第一步：属性名匹配（锁定"性格方向"）**

对每位候选人，获取其前三高属性名，统计与玩家前三属性名相同的个数（`match_count`，0~3）：

| match_count | 处理 |
|-------------|------|
| 0 或 1 | **淘汰**，不进入后续比较 |
| 2 | 性格分 = 2 × 1.2 = **2.4** |
| 3 | 性格分 = 3 × 1.2 = **3.6** |

---

**第二步：加权数值差异（锁定"发育程度"）**

对通过第一步的候选人，计算其属性值与玩家的加权差异。权重分配：

| 排名 | 权重 | 说明 |
|------|------|------|
| 第1属性 | w1 = 0.7 | 最核心的性格维度 |
| 第2属性 | w2 = 0.2 | 次要维度 |
| 第3属性 | w3 = 0.1 | 辅助维度 |

**差异值公式：**

```
diff = w1 × |候选人A1 - 玩家A1| / max(玩家A1, 1)
     + w2 × |候选人A2 - 玩家A2| / max(玩家A2, 1)
     + w3 × |候选人A3 - 玩家A3| / max(玩家A3, 1)
```

> 分母取 `max(值, 1)` 防止除零。diff 越小表示数值越接近。

**仅2项重合时的处理：**

若候选人只有2项属性名匹配（如匹配了 A1、A2，A3 不匹配），则仅计算这2项的差异，并重新归一化权重：

```
w1' = w1 / (w1 + w2) = 0.7 / 0.9 ≈ 0.78
w2' = w2 / (w1 + w2) = 0.2 / 0.9 ≈ 0.22
diff = w1' × |候选人A1 - 玩家A1| / max(玩家A1, 1)
     + w2' × |候选人A2 - 玩家A2| / max(玩家A2, 1)
```

---

**第三步：综合排序**

```
综合分 = 性格分 × (1 - diff)
```

综合分越大越相似。按综合分降序排列，从**前5名**（不足则全取）中随机抽取1位作为偶遇对象。

---

**完整示例：**

玩家：道德=15、智力=10、体质=8。前三属性：`[道德, 智力, 体质]`。

| 候选人 | 前三属性 | 道德 | 智力 | 体质 | match | 性格分 |
|--------|----------|------|------|------|-------|--------|
| 小A | 道德、智力、魅力 | 16 | 9 | — | 2 | 2.4 |
| 小B | 道德、智力、体质 | 30 | 5 | 20 | 3 | 3.6 |

**小A（2项重合，重新归一化权重）：**

```
diff_A = 0.78 × |16-15|/15 + 0.22 × |9-10|/10
       = 0.78 × 0.067 + 0.22 × 0.1
       = 0.052 + 0.022 = 0.074

综合分_A = 2.4 × (1 - 0.074) = 2.4 × 0.926 = 2.22
```

**小B（3项全中）：**

```
diff_B = 0.7 × |30-15|/15 + 0.2 × |5-10|/10 + 0.1 × |20-8|/8
       = 0.7 × 1.0 + 0.2 × 0.5 + 0.1 × 1.5
       = 0.7 + 0.1 + 0.15 = 0.95

综合分_B = 3.6 × (1 - 0.95) = 3.6 × 0.05 = 0.18
```

**结果：小A（2.22）> 小B（0.18），小A胜出。** 虽然小B性格方向完全一致，但数值偏离太大（道德过高、智力过低），不如小A"同阶段"。

#### 7.2.2 好感度规则

- 好感度是**单向**的：A对B的好感度与B对A的好感度独立计算
- 每次通过事件遇到真人时，随机增加 **1~50** 点好感度
- 首次遇到该真人时，好感度**翻倍**（2~100点）
- 对方玩家**不会感知**到被偶遇

### 7.3 待添加列表机制

当对某个角色（NPC或真人）的好感度 ≥ 100（达到LV1）时，该角色出现在"待添加列表"中。

**规则：**

| 操作 | 结果 |
|------|------|
| **添加好友** | 角色移入好友列表，好感度解除锁定，从100开始可继续正常增减 |
| **忽略** | 好感度自动调整为99，角色从待添加列表中消失 |
| **好感度下降** | 若因事件选项导致好感度降至100以下，角色自动从待添加列表移除；再次积累到100时重新出现 |

**真人好友申请流程：**

1. A对B的好感度达到100 → B出现在A的待添加列表
2. A点击"添加好友" → B收到好友申请通知
3. B选择**接受** → 双方互相加入好友列表
4. B选择**拒绝** → A收到拒绝通知，A对B的好感度调整为99

> 注意：B对A的好感度不受此流程影响，两者独立。

## 附录A：运气修正公式参考实现

```javascript
function applyLuckCorrection(min, max, luckLevel) {
    const span = max - min;
    if (span <= 1) return { min, max };
    
    const p = (luckLevel - 1) / 5;
    const actualMin = Math.round(min + p * (span - 1));
    const actualMax = Math.round(max - (1 - p) * (span - 1));
    
    return { min: actualMin, max: actualMax };
}

function randomInRange(min, max) {
    return Math.floor(Math.random() * (max - min + 1)) + min;
}
```

## 附录B：好感度等级计算

```javascript
function getFavorabilityLevel(exp) {
    // LV0: 0, LV1: 100, LV2: 300, LV3: 600, LV4: 1000...
    // LVn 所需总经验 = 100 * n(n+1)/2
    if (exp < 100) return 0;
    let n = 1;
    while (100 * n * (n + 1) / 2 <= exp) n++;
    return n - 1;
}
```
